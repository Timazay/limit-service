# Limit Service

Прототип микросервиса учёта расходов с месячным лимитом в USD.

Сервис принимает расходные операции в валюте счёта, пересчитывает их в доллары
по биржевому курсу закрытия за день операции и помечает операции, превысившие
месячный лимит. Лимит ведётся отдельно для двух категорий расхода: товаров и
услуг.

## Как запустить

### Docker Compose

Поднимает сервис вместе с PostgreSQL одной командой:

```bash
docker compose up --build
```

После старта:

- Swagger UI — <http://localhost:8080/swagger-ui.html>
- OpenAPI в JSON — <http://localhost:8080/v3/api-docs>

Схема БД накатывается Liquibase при старте приложения, отдельный шаг не нужен.

По умолчанию используется заглушка курсов (`APP_EXCHANGE_RATE_PROVIDER=stub`).
Чтобы включить реальный источник, положите ключ в `.env` в корне проекта:

```bash
TWELVEDATA_API_KEY=<ключ>
APP_EXCHANGE_RATE_PROVIDER=twelvedata
```

Файл `.env` в репозиторий не коммитится.

Остановить: `docker compose down`, с удалением данных — `docker compose down -v`.

### Локально, без Docker для приложения

Нужны JDK 21 и PostgreSQL. Базу можно поднять так:

```bash
docker run -d --name limit-pg -p 5432:5432 \
  -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=limit_db postgres:17-alpine
```

Затем:

```bash
export TWELVEDATA_API_KEY=<ключ>   # либо APP_EXCHANGE_RATE_PROVIDER=stub без ключа
./mvnw spring-boot:run
```

> Переменная `TWELVEDATA_API_KEY` нужна даже в режиме заглушки: бин
> `twelveDataRestClient` создаётся безусловно и читает это поле при старте
> контекста. Без неё приложение не поднимется.

## Часовой пояс и границы месяца

**Границы месяца считаются в часовом поясе сервиса — `Asia/Almaty` по
умолчанию, переопределяется `TIME_ZONE`.** Транзакции приходят с любым
смещением, и месяц определяется по зоне сервиса, а не по смещению клиента:

| Момент операции | Попадает в |
|---|---|
| `2022-01-31T23:59:59+06:00` | январь |
| `2022-02-01T00:00:00+06:00` | февраль |
| `2022-02-01T00:00:00+05:00` | февраль — в Алматы это уже 01:00 |

Зона задаётся в одном месте, `app.time-zone`, и оттуда расходится по трём
назначениям: бин `java.time.Clock`, границы месяца при расчёте остатка и
сериализация дат в JSON. Время в приложении не читается напрямую — только через `Clock`, иначе сценарии
с границами месяца невозможно было бы воспроизвести в тестах.

`created_at` во всех трёх сущностях задаётся сервисами из того же `Clock`, то
есть попадает в базу в зоне сервиса. В `@PrePersist` осталась страховка на
случай, если поле забыли: колонка `NOT NULL`, и дозаполнить его лучше там, чем
упасть на вставке. В приложении этот метод не срабатывает, и в `Dockerfile`
`TZ` задан лишь потому, что задаёт зону самой JVM.

## Курсы валют и обработка сбоев

Курс берётся по закрытию (`close`) за день операции. Если закрытия за этот день
нет — выходной или праздник, — используется последнее доступное закрытие
(`previous_close`).

Курсы хранятся в собственной таблице `exchange_rates` и используются из неё в
первую очередь, потому что каждый запрос к внешнему API платный и медленный.
Ключ строки — пара валют и **дата запроса**, а не дата биржевого бара: во
выходной бар отсутствует, и кэш по дате бара промахивался бы на каждой
транзакции, то есть каждый выходной оплачивался бы новым запросом.

Стратегия на случай недоступности внешнего API:

- **Таймауты.** Подключение — 5 с, чтение — 10 с. Задаются в `RestClientConfig`
  через `SimpleClientHttpRequestFactory`.
- **Повторы.** `RetryTemplate` из `spring-core`: 3 попытки, задержка 1 с с
  множителем 2, потолок 10 с. Повторяются только `RestClientException`, и
  **404 не повторяется** — пара не найдена и повтор её не найдёт.
- **Исчерпание попыток.** Ответ клиенту `502 Bad Gateway` в формате
  ProblemDetail. Транзакция при этом не сохраняется, но и не теряется: повторная
  отправка безопасна, сумма в USD пересчитается заново.
- **Внешний запрос вне транзакции БД.** Курс запрашивается до открытия
  транзакции приёма транзакции, иначе соединение с PostgreSQL удерживалось бы
  на всё время сетевых таймаутов и повторов.
- **Запись курса в своей транзакции.** Если бы она делила транзакцию приёма, её
  откат унёс бы свежий курс, и следующий запрос снова пошёл бы во внешний API за
  теми же данными.
- **Гонка двух параллельных вставок.** Уникальный индекс по
  (`currency_pair`, `rate_date`) отвергнет второй одновременный запрос; он
  возьмёт уже сохранённое значение вместо ошибки.
- **Ответы с кодом 200 и ошибкой.** TwelveData отдаёт ошибку телом ответа при
  HTTP 200, поэтому статус, код и сообщение проверяются явно. Курс вне
  разумных границ (меньше `0.000001` или больше `10000000`) считается ошибкой
  направления пары и приводит к 502, а не к нулю в базе.

Дополнительно: суммы нормализуются до двух знаков **до** деления на курс.
Иначе на некоторых значениях промежуточное округление давало бы результат,
отличающийся от округления точной дроби на копейку.

## API

Разграничения доступа нет: авторизация вынесена в отдельный микросервис и в
этом прототипе не задействована.

### Интеграционный API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/transactions` | Приём расходной операции, `201` |

```json
{
  "accountFrom": "0000000123",
  "accountTo": "9999999999",
  "currencyShortname": "KZT",
  "sum": 10000.45,
  "expenseCategory": "product",
  "datetime": "2022-01-30T00:00:00+06:00"
}
```

### Клиентский API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/v1/limits?accountFrom=…&page=…&size=…` | История лимитов клиента |
| `POST` | `/api/v1/limits` | Установка нового лимита, `201` |
| `GET` | `/api/v1/transactions/exceeded?accountFrom=…&page=…&size=…` | Транзакции, превысившие лимит |

```json
{
  "accountFrom": "0000000123",
  "expenseCategory": "product",
  "limitSum": 2000.00
}
```

Ответ на запрос превышений содержит по каждой транзакции три лимитовых поля —
`limitSum`, `limitDatetime`, `limitCurrencyShortname`. Это **тот лимит, который
действовал на момент операции**, а не последний установленный: переустановка
лимита позже не искажает ответ. У транзакций, превысивших дефолтные
1000 USD, эти поля пусты: такого лимита в таблице `limits` нет.

Ошибки возвращаются единым форматом ProblemDetail (RFC 9457) с полями
`status`, `title`, `detail` и `instance`. Ошибки валидации дополнительно
несут поле `errors` с перечислением нарушенных ограничений:

```json
{
  "type": "about:blank",
  "title": "Validation failed",
  "status": 400,
  "detail": "accountFrom: accountFrom must be 10 digits; sum: sum must be positive",
  "instance": "/api/v1/transactions",
  "errors": { "errorMessage": "accountFrom: ..." }
}
```

Неожиданная ошибка не раскрывает деталей: вместо стектрейса клиент получает
`traceId`, по которому ищется запись в логе.

Полный контракт с примерами — в Swagger UI.

## Модель данных

Схема версионируется Liquibase, подход schema first. Hibernate схему не
создаёт, а только проверяет (`ddl-auto: validate`), поэтому миграция и поле
сущности пишутся в одном коммите.

| Таблица | Назначение |
|---|---|
| `transactions` | Операции: счета, сумма, сумма в USD, категория, момент, признак превышения, ссылки на лимит и курс |
| `limits` | История лимитов клиента: категория, сумма в USD, дата установки |
| `exchange_rates` | Кэш курсов: пара, дата, закрытие, предыдущее закрытие, источник |

Остаток лимита и действующий лимит считаются одним SQL-запросом с подзапросом
и агрегатом: лимит берётся подзапросом с `LIMIT 1` и сортировкой по дате
установки, израсходованное — `SUM` за границы месяца.

Перерасчёт при параллельных запросах исключён advisory-блокировкой
`pg_advisory_xact_lock` на ключ «клиент + категория + месяц»: остаток — это
агрегат, и строку в нём заблокировать нельзя. Ключ содержит первое число
месяца, поэтому весь месяц клиента сериализуется одним ключом, а транзакции
разных клиентов ждать друг друга не заставляют.

## Тесты

```bash
./mvnw test      # юнит-тесты, Docker не нужен
./mvnw verify    # плюс сквозной тест с PostgreSQL в Testcontainers, нужен Docker
```

`maven-failsafe-plugin` запускает по суффиксу `IT`, поэтому быстрый цикл
`./mvnw test` не требует Docker, а полный набор запускается стандартной командой
сборки, как требует задание.

Сейчас 62 юнит-теста и один сквозной.

Сквозной тест `ExceededTransactionsApiIT` целиком воспроизводит «1 случай» из
задания через HTTP: приложение на реальном порту, PostgreSQL в Testcontainers,
внешний API курсов замокан WireMock. Проверяется, что превысили ровно две
операции — 3 января и 13 января — и у каждой в ответе тот лимит, который
действовал тогда: 1000 USD от 1 января и 2000 USD от 10 января.

Лимиты в нём ставятся прямой вставкой в `limits`. Через API `limit_datetime`
проставился бы серверной датой «сейчас», и лимит января 2022 года не нашёлся бы
для транзакций того же года. Это следствие требования «клиент не может выставить
дату в прошлом», а не обход проверки.

Покрытые граничные случаи расчёта лимита:

- остаток ровно 0 не считается превышением, сравнение строгое;
- новый лимит внутри месяца сравнивается со всем расходом месяца, а не только с
  расходом после его установки;
- смена месяца обнуляет остаток;
- граница полуночи в поясе сервиса;
- весь месяц клиента сериализуется одним ключом блокировки.

## Структура проекта

```
src/main/java/by/timofeyzaytsev/limitservice/
├── client/            интерфейс источника курсов и его реализации
├── config/            бины конфигурации, @ConfigurationProperties
├── controller/        REST API
├── dto/               запросы и ответы, они же схемы OpenAPI
├── exception/         ApiException и обработка ошибок в ProblemDetail
├── mapper/            преобразование сущностей в DTO (MapStruct)
├── model/             сущности JPA и enums
├── repository/        Spring Data JPA, нативные запросы, проекции
├── service/           бизнес-логика, транзакционная часть вынесена отдельно
└── utils/             вспомогательные методы

src/main/resources/db/changelog/   миграции Liquibase
src/test/java/.../utils, service   юнит-тесты
src/test/java/.../it/              тесты с БД и внешним API
```

Приём транзакции разделён на два слоя намеренно: `TransactionServiceImpl`
пересчитывает сумму и обращается к внешнему API, `TransactionProcessorImpl` —
транзакционная часть с блокировкой и выставлением флага. Так внешний запрос не
удерживает соединение с базой.

## AI в проекте

**Инструмент:** opencode. Использовался для написания тестов, скиллов и
инфраструктуры, а также для проверки гипотез по документации библиотек.

**MCP:** подключён `context7` — поиск актуальной документации по библиотекам.
Конфигурация в `opencode.json`, ключ не требуется.

Где он реально помог: при добавлении интеграционных тест выяснилось, что Spring
Boot 4.1.1 управляет Testcontainers **2.0.5**, где модули переименованы —
`org.testcontainers:postgresql` и `:junit-jupiter` больше не существуют, нужны
`testcontainers-postgresql` и `testcontainers-junit-jupiter`. Без сверки с
документацией сборка просто не скомпилировалась бы.

**Скиллы.** Четыре скилла в `.agents/skills/` — это открытый формат Agent
Skills, одинаковый для Codex, Cursor, Claude Code и Copilot. opencode видит их
через `opencode.json → skills.paths`, остальные инструменты — по стандартным
путям, перечисленным в приложении задания.

| Скилл | Когда применять |
|---|---|
| `write-test` | Любой тест: нейминг, AssertJ, Mockito, работа с `Clock`, тестовые зависимости |
| `write-limit-logic-test` | Тесты расчёта `limit_exceeded` и границ месяца |
| `create-db-migration` | Новая миграция Liquibase |
| `add-exchange-rate-provider` | Новый источник курсов валют |

Пример: задача «добавить провайдера курсов» раскладывается скиллом
`add-exchange-rate-provider` — какой интерфейс реализовать, где зарегистрировать
бин, какие тесты написать. Скилл ссылается на конкретные классы и команды
проекта, а не на общие советы, и содержит известные ловушки проекта.

**Что написано вручную:** вся бизнес-логика и её объяснение — расчёт остатка
одним SQL-запросом с подзапросом и агрегатом, advisory-блокировка месяца,
схема БД и миграции, поведение при превышении лимита внутри месяца. Это то, за
что отвечаю на собеседовании.

**Где AI ошибся и как это заметили.** Все четыре случая поймали тесты, а не
ревью кода:

1. Утверждал, что для тестов расчёта лимита достаточно подменить бин `Clock`.
   Неверно: границы месяца считает `monthStartOf`, и она берёт зону из
   `AppProperties`, а не из часов. Поймали два упавших теста на границах месяца.
2. Написал в скилле, что полночь 1 февраля по смещению `+06:00` приходится на
   31 января. В зоне сервиса это 1 февраля. Поймал тест на границе полуночи.
3. Предложил `wiremock-jetty12` для мока внешнего API. Не взлетело:
   `NoSuchMethodError` — версия Jetty, управляемая Boot, не совпадает с той,
   которую ждёт WireMock. Сработал `wiremock-standalone`, шивающий Jetty внутрь.
4. Не заметил, что без `<proc>full</proc>` процессоры аннотаций на JDK 21 не
   запускаются: MapStruct молча не создаёт `*MapperImpl`, сборка проходит, а
   контекст падает на отсутствии бина маппера. Ошибка выглядела как проблема
   зависимостей, а не сборки.

**Узкое место.** OpenAPI до правки не работал: `/v3/api-docs` отдавал 500 из-за
несовместимости springdoc 2.x с Spring Framework 7, а Swagger UI отдавался и
выглядел рабочим, пока не загружал спецификацию. Нашёл это только запуском
приложения и запросом к эндпойнту — сборка была зелёной. Вывод: наличие
зависимости в `pom.xml` ничего не значит, поведение интеграционных бинов
проверяется запуском.

## Известные ограничения

- **Пагинация списка превышений выполняется в памяти.** Запрос использует
  `LEFT JOIN FETCH` вместе с `Pageable`, а Hibernate не умеет строить
  постраничный запрос с `JOIN FETCH`: он выдаёт `HHH90003004` и применяет
  `LIMIT` уже к загруженному списку. На текущих объёмах незаметно, но с ростом
  данных будет упираться в память. Общее число превышений считается отдельным
  запросом — `count` с `JOIN FETCH` Hibernate тоже не строит.
- **Лимит нельзя отозвать или удалить.** Обновление запрещено заданием, поэтому
  у клиента нет способа отключить лимит, кроме как установить меньший.
- **Ограничение размера страницы задано только на уровне API.** В самом запросе
  параметра `size` нет, поэтому ограничение в 100 записей держится на
  `@Max(100)` в контроллере и не защищает БД при прямом обращении.
- **Разграничения доступа нет** — по условию задачи авторизация в другом
  микросервисе.
- **Интеграционные тесты требуют Docker.** Причина не в коде, а в том, что
  Testcontainers запускает настоящую PostgreSQL.
